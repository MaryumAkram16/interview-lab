MVCC — How PostgreSQL Handles Concurrency
📸 MVCC (Multi-Version Concurrency Control) is like a photo system. When you start a transaction, you get a snapshot of the database at that exact moment. Other transactions can write new versions of rows without blocking you — you keep reading your snapshot. No locks needed for reads.

MVCC = readers don't block writers, writers don't block readers. Each transaction sees a consistent snapshot of the database as it was when the transaction started.

Optimistic Locking Pattern
🏷️ Optimistic locking adds a version number to each row. When you update, you check the version hasn't changed since you read it. If it has, someone else updated it first — your update fails and you retry. No blocking, just detection.
-- Add version column to table
ALTER TABLE appointments
  ADD COLUMN version INTEGER DEFAULT 1;

-- Read with version
SELECT id, status, version
  FROM appointments
 WHERE id = 42;
-- Returns: id=42, status='pending', version=3

-- Update — only if version unchanged
UPDATE appointments
   SET status = 'confirmed',
       version = version + 1
 WHERE id = 42
   AND version = 3;  -- must match!

-- Check rows affected
-- 0 rows updated = someone else changed it first
-- 1 row updated = success, proceed
Python — Optimistic Lock with Retry
def confirm_appointment(conn, appt_id, max_retries=3):
    for attempt in range(max_retries):
        with conn.cursor() as cur:
            # Read current version
            cur.execute(
                "SELECT version FROM appointments WHERE id=%s",
                (appt_id,)
            )
            row = cur.fetchone()
            current_version = row[0]

            # Try to update with version check
            cur.execute("""
                UPDATE appointments
                   SET status='confirmed',
                       version=version+1
                 WHERE id=%s AND version=%s
            """, (appt_id, current_version))
            conn.commit()

            if cur.rowcount == 1:
                return True   # success
            # rowcount=0 → retry

    raise RuntimeError("Failed after retries")

🎤 Q: "How does PostgreSQL handle concurrent transactions?"
PostgreSQL uses MVCC — Multi-Version Concurrency Control. Every transaction gets a snapshot of the database at the moment it starts. Readers never block writers and writers never block readers because each transaction works with its own version of the data. For explicit write conflicts I use SELECT FOR UPDATE to lock specific rows, or INSERT...ON CONFLICT for atomic deduplication. For high-throughput systems like job queues I use SKIP LOCKED so multiple workers can process different rows in parallel without blocking each other.
