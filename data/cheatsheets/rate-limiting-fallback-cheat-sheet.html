Rate Limiting Concepts
🚰 Rate limiting is a tap on a water pipe. The API provider sets a flow rate — you can only pull so many requests per second. If you exceed it, the tap closes (429). Your job is to respect the flow rate and not force the tap open.
Common Rate Limit Algorithms
AlgorithmHow It WorksUsed By
Token BucketTokens refill at fixed rate. Each request uses one token. Burst allowed when full.OpenAI, AWS
Fixed WindowX requests per minute. Counter resets every 60s.Simple APIs
Sliding WindowX requests per any rolling 60s window. No reset spike.Stripe, GitHub
Leaky BucketRequests queue up and process at a fixed rate. Smooth output.Network devices
Client-Side Rate Limiter
import time

class RateLimiter:
    """Token bucket — limits calls per second"""
    def __init__(self, calls_per_second):
        self.rate  = calls_per_second
        self.tokens = calls_per_second
        self.last_check = time.time()

    def acquire(self):
        now = time.time()
        elapsed = now - self.last_check
        self.last_check = now

        # Refill tokens based on elapsed time
        self.tokens = min(
            self.rate,
            self.tokens + elapsed * self.rate
        )
        if self.tokens >= 1:
            self.tokens -= 1
            return True

        # Not enough tokens — wait
        wait = (1 - self.tokens) / self.rate
        time.sleep(wait)
        self.tokens = 0
        return True

# Use it — max 5 calls per second
limiter = RateLimiter(calls_per_second=5)

for item in batch_of_items:
    limiter.acquire()   # wait if needed
    call_openai(item)
Fallback Strategies
🛟 A fallback is your life jacket when the boat sinks. When the primary API fails, you don't crash the whole system — you gracefully switch to a backup: cached data, a different provider, or a safe default response.
Strategy 1 — Cached Response Fallback
import requests

cache = {}   # In production: Redis

def get_with_cache_fallback(url, cache_key):
    try:
        resp = requests.get(url, timeout=5)
        resp.raise_for_status()
        data = resp.json()

        # Store fresh result in cache
        cache[cache_key] = data
        return data

    except Exception as e:
        # API failed — try cache
        if cache_key in cache:
            print(f"API failed, returning cached data")
            return cache[cache_key]

        # No cache either — raise
        raise RuntimeError("API + cache both failed")
Strategy 2 — Provider Switching (AI Fallback)
import openai, google.generativeai as genai

def llm_with_fallback(prompt):
    # Try OpenAI GPT-4o first
    try:
        client = openai.OpenAI()
        resp = client.chat.completions.create(
            model="gpt-4o",
            messages=[{"role":"user","content":prompt}]
        )
        return resp.choices[0].message.content

    except Exception as e:
        print(f"GPT-4o failed: {e}. Trying Gemini...")

    # Fallback to Google Gemini
    try:
        model = genai.GenerativeModel("gemini-1.5-pro")
        resp  = model.generate_content(prompt)
        return resp.text

    except Exception as e:
        print(f"Gemini also failed: {e}")

    # Both failed — return safe default
    return "I'm unable to process your request right now."
🔗 This is exactly your MediLens architecture MediLens uses both Gemini and can fall back to OpenAI. This pattern is production-grade and you can speak to it directly in your interview: "In MediLens I implemented provider fallback — if Gemini returns a 503, the system retries with GPT-4o before showing an error to the patient."
Graceful Degradation
✈️ Graceful degradation is like a plane losing one engine but still flying. The system keeps working at reduced capacity instead of crashing completely. Show the user something useful even when parts are broken.
Strategy 3 — Default Safe Response
def get_ai_triage(patient_symptoms):
    try:
        return call_gemini_triage(patient_symptoms)

    except Exception:
        # AI unavailable — safe fallback message
        # Don't expose error to patient
        return {
            "triage_level": "unknown",
            "message": (
                "Our AI system is temporarily unavailable. "
                "A staff member will assist you shortly."
            ),
            "action": "escalate_to_human"
        }

import requests

def alert_slack(message, webhook_url):
    try:
        requests.post(
            webhook_url,
            json={"text": f"🚨 ALERT: {message}"},
            timeout=5
        )
    except:
        pass  # Don't let alert failure crash app

Master Interview Answers
🎤 Q: "How do you handle rate limiting in a production AI pipeline?"
Three layers. First, client-side rate limiting — a token bucket that spaces out requests to stay under the API's limit before hitting 429. Second, when I do get a 429, I read the Retry-After header and sleep exactly that long before retrying. Third, for batch processing I queue jobs and process at a controlled rate. In my n8n workflows I add deliberate delays between AI calls to avoid rate limits entirely.
🎤 Q: "What is graceful degradation? Give an example from your work."
Graceful degradation means the system keeps working at reduced functionality when a component fails, instead of crashing entirely. In MediLens, if the Gemini triage AI is unavailable, the system doesn't show an error to the patient — it returns a safe default message and escalates to a human staff member. The workflow keeps running, the patient gets helped, and Slack gets an alert so the team can investigate.
✅ One-line summary Rate limiting: respect API quotas with token bucket + Retry-After header. Fallback strategies: cached data → provider switch → safe default → human escalation. Never let one failed API call crash your whole pipeline. Alert Slack silently, always return something useful to the user.
