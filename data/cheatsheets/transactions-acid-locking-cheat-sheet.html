Transactions
🏦 A transaction is like a bank transfer. Moving £500 from Account A to Account B involves two steps: debit A, credit B. If the power goes out after the debit but before the credit, you've lost £500. A transaction wraps both steps — either both succeed, or neither happens.

A transaction groups multiple SQL operations into one atomic unit — all succeed together or all fail together.

-- Basic transaction structure
BEGIN;           -- start transaction

UPDATE accounts
   SET balance = balance - 500
 WHERE id = 'account_a';

UPDATE accounts
   SET balance = balance + 500
 WHERE id = 'account_b';

COMMIT;          -- make permanent
-- OR: ROLLBACK; to undo everything

-- Always handle errors with rollback
BEGIN;

UPDATE appointments
   SET status = 'confirmed'
 WHERE id = 123;

INSERT INTO notifications (patient_id, message)
VALUES (456, 'Your appointment is confirmed');

-- If any step fails, undo everything
-- ROLLBACK; ensures no partial update

COMMIT;
⚠️ Without transactions — the danger If you UPDATE the appointment status but the INSERT into notifications crashes halfway, you have a confirmed appointment with no notification sent. The patient never shows up. Transactions prevent this inconsistent state.
Row-Level Locking
🔒 SELECT FOR UPDATE puts a padlock on a row while you read it. Anyone else trying to read or write that row with FOR UPDATE must wait until you commit. This prevents two transactions from simultaneously deciding they can both take the last appointment slot.
SELECT FOR UPDATE — Prevent Race Conditions
-- Book the last available seat safely
BEGIN;

-- Lock this row — no one else can touch it
SELECT * FROM appointment_slots
 WHERE id = 42
   AND available = TRUE
   FOR UPDATE;  -- row lock acquired here

-- Now safe to update — no race condition
UPDATE appointment_slots
   SET available = FALSE,
       patient_id = 789
 WHERE id = 42;

COMMIT;  -- lock released here
SKIP LOCKED — Non-Blocking Queue
-- Process jobs from a queue without blocking
-- Multiple workers can run in parallel
BEGIN;

SELECT * FROM job_queue
 WHERE status = 'pending'
 LIMIT 1
   FOR UPDATE
   SKIP LOCKED;  -- skip rows locked by other workers

-- This worker gets a row no other worker is processing
UPDATE job_queue SET status = 'processing'
 WHERE id = [fetched_id];

COMMIT;

💡 In your Supabase projects When MediLens books appointments, two patients could click "Book" simultaneously. SELECT FOR UPDATE in the booking transaction ensures only one gets the slot. The other transaction waits, then sees the slot is gone and returns "no availability."

Deadlocks — How They Happen + Fix
-- DEADLOCK: Transaction A and B block each other
-- T-A: locks row 1, then tries to lock row 2
-- T-B: locks row 2, then tries to lock row 1
-- Both wait forever → PostgreSQL kills one

-- ✅ Fix: always lock rows in the same order
-- Both transactions lock row 1 first, then row 2
-- One waits, other completes — no deadlock

SELECT * FROM resources
 WHERE id IN (1, 2)
 ORDER BY id        -- consistent order!
   FOR UPDATE;
Master Interview Answers
🎤 Q: "What are ACID properties?"
ACID stands for Atomic, Consistent, Isolated, Durable. Atomic means all operations in a transaction succeed or all fail — no partial writes. Consistent means the database stays in a valid state before and after. Isolated means concurrent transactions don't see each other's intermediate states — preventing race conditions. Durable means committed data survives crashes. PostgreSQL and Supabase are fully ACID compliant.
🎤 Q: "What is SELECT FOR UPDATE and when do you use it?"
SELECT FOR UPDATE acquires a row-level lock when you read a row. Any other transaction trying to update that row — or lock it themselves — must wait until your transaction commits. I use it for the appointment booking flow in MediLens: read the available slot with FOR UPDATE, then update it to booked. Without it, two patients could simultaneously read the same slot as available and both book it, causing a double-booking.
✅ One-line summary Transaction = BEGIN + operations + COMMIT (or ROLLBACK). ACID = Atomic + Consistent + Isolated + Durable. SELECT FOR UPDATE = row lock for read-then-write safety. SKIP LOCKED = parallel queue workers. Deadlock fix = always acquire locks in the same order across all transactions.
