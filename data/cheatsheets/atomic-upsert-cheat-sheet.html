What is an Atomic Upsert?
🚦 Analogy: Two cars race to park in the last spot. Without atomicity, both think the spot is free and both try to park — crash. An atomic upsert is like a traffic light: only one car gets the spot, the other is handled cleanly. It all happens in one uninterruptible step.

An upsert = INSERT if record doesn't exist, UPDATE if it does — in a single atomic operation.

Atomic means the check and the write happen as one uninterruptible unit. No other process can slip in between. This is crucial for preventing the "row doesn't exist yet" race condition, where multiple concurrent requests might try to create the same record, leading to duplicates or data corruption.

The Race Condition Problem (Without Atomicity)
❌ BROKEN — 2 steps
1. SELECT → record exists?
2. If no → INSERT

Problem: Two threads both pass step 1 before either writes → both INSERT → duplicate! This is the classic "row doesn't exist yet" race condition.
✅ SAFE — 1 atomic step
INSERT...ON CONFLICT
→ check + write happen
together, uninterruptible.
Database guarantees only one wins.
Basic Syntax — PostgreSQL
-- INSERT...ON CONFLICT: the atomic upsert
INSERT INTO users (email, name, updated_at)
VALUES ('maryum@email.com', 'Maryum', now())

ON CONFLICT (email)   -- conflict on this column

-- Option A: do nothing if already exists
DO NOTHING;

-- Option B: update specific fields
DO UPDATE SET
    name       = EXCLUDED.name,
    updated_at = EXCLUDED.updated_at;
💡 EXCLUDED = the row that was rejected When a conflict happens, PostgreSQL calls the incoming (rejected) row EXCLUDED. You can reference its columns in the DO UPDATE SET clause to use the new values.

Real Code Patterns
Pattern 1 — Idempotency Key Storage
-- Store a processed request key
-- If same key comes again → silently ignore
INSERT INTO idempotency_keys
    (key, result, created_at)
VALUES
    ($1, $2, now())
ON CONFLICT (key)
DO NOTHING;

-- Then check if the row was actually inserted
-- or if it already existed:
-- rows_affected = 0 means it was a duplicate
Pattern 2 — User Record Upsert
-- Create user on first login
-- Update last_login on repeat visits
INSERT INTO users
    (user_id, email, name, last_login)
VALUES
    ($1, $2, $3, now())
ON CONFLICT (user_id)
DO UPDATE SET
    last_login = now(),
    name       = EXCLUDED.name
RETURNING *;  -- get the final row back
Pattern 3 — Python with psycopg2
import psycopg2

def upsert_patient(conn, patient_id, data):
    with conn.cursor() as cur:
        cur.execute("""
            INSERT INTO patients
                (patient_id, name, phone)
            VALUES (%s, %s, %s)
            ON CONFLICT (patient_id)
            DO UPDATE SET
                name  = EXCLUDED.name,
                phone = EXCLUDED.phone
            RETURNING patient_id, name;
        """, (patient_id,
               data["name"],
               data["phone"]))
        conn.commit()
        return cur.fetchone()

Race Conditions & Locking
What is a Race Condition?
🏃 Two processes read the same data at the same time, both decide to write, and they overwrite each other. The result depends on who finishes last — unpredictable, dangerous. 
-- ❌ RACE CONDITION — two separate steps
-- Thread A and Thread B both run this
SELECT * FROM seats WHERE id = 1;
-- both see: available = true
UPDATE seats SET available = false
WHERE id = 1;
-- both update! Seat double-booked 💥

-- ✅ FIX — SELECT FOR UPDATE (row lock)
BEGIN;
SELECT * FROM seats
WHERE id = 1
FOR UPDATE;  -- locks this row
-- Thread B now WAITS here
UPDATE seats SET available = false
WHERE id = 1;
COMMIT;      -- lock released, Thread B continues

Master Interview Answers
🎤 Q: "What is an atomic upsert and why does it matter?"
An atomic upsert is a single database operation that either inserts a new record or updates an existing one — the check and the write happen together as one uninterruptible step. Without atomicity, two concurrent requests could both check, both see no record exists, and both insert — creating a duplicate. INSERT...ON CONFLICT in PostgreSQL solves this. I use Supabase's .upsert() in my projects which generates this SQL automatically.
🎤 Q: "What is the difference between DO NOTHING and DO UPDATE?"
DO NOTHING silently ignores the new data if a conflict occurs — perfect for idempotency keys where you only want to store the result once. DO UPDATE replaces or merges specific columns with the new values — perfect for user profiles where you want to update last_login or refresh a token on every request. EXCLUDED refers to the incoming row that caused the conflict.
🎤 Q: "How does SELECT FOR UPDATE prevent race conditions?"
SELECT FOR UPDATE acquires a row-level lock the moment you read it. Any other transaction trying to read the same row with FOR UPDATE will wait until your transaction commits. This makes the read-then-write pattern safe — no other process can change the row between your SELECT and your UPDATE. It's the right tool when INSERT...ON CONFLICT isn't enough, like booking the last seat in a concert.
✅ One-line summary to memorize Atomic upsert = INSERT...ON CONFLICT — single uninterruptible check-and-write. Prevents duplicates from concurrent requests. DO NOTHING = ignore duplicate. DO UPDATE = merge new values. Used in Supabase via .upsert(). Race condition prevention tool #1.
