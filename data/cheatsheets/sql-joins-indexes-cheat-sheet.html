Joins
🔗 Joins combine rows from two tables based on a matching column. INNER JOIN = only matching rows in both. LEFT JOIN = all left rows + matching right rows (NULL if no match). Think of it as a Venn diagram — INNER = intersection, LEFT = entire left circle.
INNER JOIN — Only Matching Rows
-- Get all appointments WITH patient info
-- Appointments without a patient are excluded
SELECT
    a.id, a.slot_time, a.status,
    p.name, p.phone
FROM appointments a
INNER JOIN patients p
        ON a.patient_id = p.id;
LEFT JOIN — All Left + Matching Right
-- Get ALL patients, with their appointment if any
-- Patients with no appointment → NULL in appt columns
SELECT
    p.name,
    a.slot_time,        -- NULL if no appointment
    a.status
FROM patients p
LEFT JOIN appointments a
       ON p.id = a.patient_id;
All Join Types
JoinReturns
INNER JOINOnly rows matching in BOTH tables
LEFT JOINAll left rows + matching right (NULL if none)
RIGHT JOINAll right rows + matching left (NULL if none)
FULL JOINAll rows from both, NULL where no match
CROSS JOINEvery combination (cartesian product)
Self Join + Subquery
-- Find patients who have multiple appointments
SELECT patient_id, COUNT(*) appt_count
  FROM appointments
 GROUP BY patient_id
HAVING COUNT(*) > 1;

-- Subquery in WHERE
SELECT * FROM patients
 WHERE id IN (
    SELECT patient_id
      FROM appointments
     WHERE status = 'urgent'
 );
Indexes
📖 An index is like the index at the back of a book. Without it, you read every page (full table scan). With it, you jump directly to the right page (O(log n) lookup). The tradeoff: indexes make reads faster but writes slightly slower.
Creating Indexes
-- B-Tree index (default) — equality + range
CREATE INDEX idx_patient_email
          ON patients(email);

-- Unique index — enforces uniqueness
CREATE UNIQUE INDEX idx_appt_slot
               ON appointments(slot_id);

-- Composite index — queries using both columns
CREATE INDEX idx_appt_patient_date
          ON appointments(patient_id, slot_time);

-- Partial index — only indexes certain rows
-- Smaller, faster for filtered queries
CREATE INDEX idx_urgent_appts
          ON appointments(created_at)
       WHERE status = 'urgent';

-- GIN index — for JSONB, arrays, full-text
CREATE INDEX idx_symptoms_gin
          ON patients USING GIN (symptoms);
Index Types
TypeBest For
B-TreeDefault. Equality, range, ORDER BY

EXPLAIN ANALYZE — Diagnose Slow Queries
-- See query execution plan + actual timings
EXPLAIN ANALYZE
SELECT * FROM appointments
 WHERE patient_id = 123
   AND status = 'confirmed';

-- Look for:
-- "Seq Scan" = bad (full table scan, no index)
-- "Index Scan" = good (using index)
-- "Bitmap Heap Scan" = good for range queries
-- High "rows=" with low "actual rows=" = bad estimate
Advanced SQL Patterns
Window Functions
-- Rank patients by number of appointments
SELECT
    patient_id,
    COUNT(*) appt_count,
    RANK() OVER (
        ORDER BY COUNT(*) DESC
    ) AS rank
FROM appointments
GROUP BY patient_id;

-- Running total
SELECT
    created_at::date AS day,
    COUNT(*) bookings,
    SUM(COUNT(*)) OVER (
        ORDER BY created_at::date
    ) AS running_total
FROM appointments
GROUP BY created_at::date;
CTEs — Readable Complex Queries
-- CTE: Common Table Expression
-- Like a named subquery — improves readability
WITH urgent_patients AS (
    SELECT DISTINCT patient_id
      FROM appointments
     WHERE triage_level = 'urgent'
),
recent_visits AS (
    SELECT patient_id, MAX(slot_time) last_visit
      FROM appointments
     GROUP BY patient_id
)
SELECT p.name, r.last_visit
  FROM patients p
  JOIN urgent_patients u ON p.id = u.patient_id
  JOIN recent_visits r   ON p.id = r.patient_id;
Master Interview Answers
🎤 Q: "What is the difference between INNER JOIN and LEFT JOIN?"
INNER JOIN returns only rows where there's a match in both tables — unmatched rows from either side are excluded. LEFT JOIN returns every row from the left table, with matching data from the right table where it exists, and NULL where it doesn't. Use LEFT JOIN when you need all records from one table regardless of whether the related record exists — for example, all patients even if they have no appointments yet.
🎤 Q: "When should you add an index?"
Add indexes on columns you frequently filter by in WHERE clauses, JOIN conditions, and ORDER BY. In my Supabase projects I always index patient_id and email since nearly every query filters by those. The tradeoff: indexes speed up reads but slow down inserts and updates slightly, and consume storage. Use EXPLAIN ANALYZE to confirm a query is doing a Seq Scan — that's the signal an index is needed.
✅ One-line summary INNER JOIN = intersection only. LEFT JOIN = all left + matched right. Always index WHERE and JOIN columns. B-Tree = default index for most use. GIN = JSONB/arrays. EXPLAIN ANALYZE reveals Seq Scan (bad) vs Index Scan (good). CTEs make complex queries readable.
